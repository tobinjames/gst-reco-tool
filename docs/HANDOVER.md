# GST Annual Return & ITC Reconciliation Tool — Handover

James & James LLP · built 20 Nov 2026 · Loader v0.14 (saved workpapers bring back their files and settings, 21 Nov 2026), workbook template 2026.11.20-7

## What it is
Two pieces:
1. **GST_Annual_Return_Loader.html**: a single offline HTML page (Chrome / Edge; no install, no Excel 365 needed; files never leave the PC). It has three tabs (v0.9) that share one file pool; files of a GSTIN other than the client's are warned about and ignored in every tab:
   - **Input Reco** (monthly ITC reconciliation): GSTR-2B JSON(s) for one or more months, plus purchase register(s) in any format (column mapping), produce *ITC_Recon_<GSTIN>_<period>.xlsx*. That workbook has Summary (ITC position and claimable ITC), Recon_Purchases, Recon_Suppliers, Month_wise, Books_Purchase and RAW_2B.
   - **Annual return**: GSTR-1 JSON/ZIP (PY, CY, NY), GSTR-2B JSON (CY + NY Apr–Oct), GSTR-3B PDFs, the portal auto-drafted GSTR-9 JSON and registers produce *GSTR9_<GSTIN>_<FY>.xlsx*. Step 04 reads the finished, saved workbook back and produces the **GSTR-9 upload JSON**, with an edit check (formulas vs template, fingerprint + HMAC seal of imported data, audit list of adjustments).
   - **GST ledger flow** (v0.9): the portal Electronic Credit Ledger, Cash Ledger and Liability Register (CSV / Excel) against the books GST ledgers (Tally voucher dump, Zoho detailed GL, or any single-ledger export with Date / Particulars / Debit / Credit). It shows the flow (opening, output tax, RCM, credit notes, ITC availed / reversed / reclaimed / set off / refunded, cash deposits and use, interest / late fee / penalty, closing) as per books, as per portal and the difference, explains every difference from the entries, runs cross-checks, and writes *GST_Flow_<GSTIN>_<FY>.xlsx*. See "GST ledger flow" below.
2. **GST_Annual_Return_Workbook.xlsx**: the macro-free template (Excel 2010+), embedded in the loader.

   - **Revenue reco** (v0.11): books vs GSTR-1 vs GSTR-3B for one FY, with a dashboard, two bank-reco style statements and the reason for each difference. See "Revenue reco" below.

## Working on it
From `loader/`: `npm ci` once, then
- `npm run check` before every PR: formatting, type check, all tests, build. GitHub runs the same check on each pull request (.github/workflows/ci.yml) and attaches the built HTML to the run.
- `npm test` tests only; `npm run test:update` after an intended change to a real-file case's results (then read the expected.json diff).
- `npm run format` tidies the code (Prettier); `npm run build` produces `dist/index.html`.
- Workbook template change: `python3 workbook/build_workbook.py` (or build_itc_template.py) from anywhere; it writes straight into loader/template and loader/src.
- Release: the built HTML is not committed. Run the Release workflow from the Actions tab with a version (e.g. `v0.10`), or push that tag; .github/workflows/release.yml publishes a GitHub Release with GST_Reco_Loader_<tag>.html. Copies for Tobin also go to the project files (releases/).

## GST ledger flow (v0.9, agreed with Tobin)
- Single GSTIN, one FY with a month filter (From / To). Portal entries count by **return period** (liability register: the period in the ARN; credit / cash ledger: the return the entry belongs to), books by voucher date unless the user moves a line to another return period.
- Books accounts: GST-looking ledgers are picked by name (rate-wise ledgers like Output CGST 9% add up under their head; value ledgers like "IGST Sales 12%" are not GST accounts); the user confirms the type and head of each. Non-accounting vouchers (orders, delivery / receipt notes, memorandum) are left out.
- Balances: single-ledger exports and the portal's Opening Balance rows give balances; GL dumps don't, so the user enters openings (and closings to check against the trial balance). Entered balances go to the Audit sheet.
- Three statements: Flow as per books, Flow as per portal, Difference (with the unexplained part per row).
- Reconciliation (redesigned after Tobin's review of a real client, Nov 2026; row-level "reconciling items" were not actionable). Five steps, same on screen (card 7) and in Excel:
  1. Set-up checks (src/flow/year.ts): missing portal ledgers, books accounts with no opening where the portal has one, lines not placed in a flow row, ledger coverage gaps, no 2B loaded.
  2. Year comparison (year.ts `yearRecon`): one line per movement (ITC net of reversals, set-off, output tax net of credit notes, RCM, tax paid by ITC / cash, deposits, fees), books vs portal for the year, the year-end cut-off (engine 'After the period' items) and the rest "to look at", with a month drill-down and running difference; Show lines opens the books / portal lines of a month, with Change + remark.
  3. ITC three ways (src/flow/itc3.ts `itcThreeWay`): books invoices are built from the purchase vouchers in the GL dump (ITC-availed lines grouped by voucher, supplier = the party line, invoice no. = Tally reference or voucher no.) and matched to GSTR-2B with reconPurchases (src/recon.ts), giving a bridge books → 2B (entries without invoice, not in 2B, 2B only, value differences); 2B → 3B is month by month against the credit ledger. A purchase register, when loaded, is only a cross-check of the total.
  4. Suggested journals (year.ts JGROUPS): set-off, cash payments / fees, deposits / refunds, ITC refund, dated the period end, balancing to Suspense / Bank where the books have no other side. Not posted anywhere.
  5. Closing statement: closing as per books + journals = adjusted, less each remaining line (opening difference, cut-off, ITC / output tax differences, head split), = closing as per portal, with a nil check.
- Reasons are worked out from the entries, never typed: opening, netted on portal (reversals / RCM / credit notes), tax head (incl. cross-utilisation), timing (month to month), after the period, fee booked to tax, then unexplained. The user can change only the records behind a reason (flow row within the allowed rows for the account type, tax head, return period) with a required remark; changes are logged to Audit and kept in the browser per GSTIN + FY. Lines no rule can place go to "Not mapped" for the user to pick a row.
- Cross-checks: cash ledger vs liability paid in cash, credit ledger vs liability paid by ITC, credit ledger vs GSTR-3B 4C and liability register vs 3B 6.1 (when 3B PDFs are loaded); plus coverage and start-date warnings.
- Workbook: Read Me, Setup_Checks, Year_Compare, ITC_3way, ITC_Invoices, Journals, Closing, Flow_Books, Flow_Portal, Flow_Difference, Cross_Checks, Month_wise, Books_Lines, Portal_Lines, Balances, Audit. Year_Compare and the flow sheets are SUMIFS over Books_Lines / Portal_Lines / Balances; Closing links to the flow sheets and Journals. Tested by `npx tsx test/flow.ts` (planted differences, journals, closing, 3-way ITC on the demo 2B) and `python3 test/flow_recalc.py <workbook>` (0 mismatches over 2,658 formulas).
- Real client samples were used only locally and are not in the repo.

## Revenue reco (v0.11, agreed with Tobin 21 Nov 2026)
- Books source: the sales register (mapped under "Map register columns") when there is one; only without it, a day book / GL dump /
  detailed ledgers (flow/books.ts reader). Revenue ledgers are suggested by name (sales, other income; interest, dividends, forex =
  "not a supply"); the user sets each ledger's class (taxable, export, exempt, non-GST, not a supply, not revenue = ignore). Invoices are
  one per voucher and class, tax from the Output GST lines of the voucher. GL dumps carry no GSTIN, so taxable invoices not found in
  GSTR-1 B2B / B2CL are taken as B2C of their month. If both are loaded, the GL dump is only a control total.
- Customer names (step 3b, src/revenue/customers.ts, as Input Reco does for suppliers): GSTR-1 JSON has the customer GSTIN but no
  name, so names are learnt from the books (entries carrying the GSTIN, and invoices whose number is in GSTR-1 under one GSTIN).
  Exact names are applied automatically; approximate names (nameScore) and invoice-no. hits are suggested; the user can pick any GSTR-1
  customer by hand or mark a customer unregistered (B2C). Confirmed names are kept in the browser per client GSTIN.
- Customer list (kind 'Customer list', parseCustomerList): any sheet with a name column and a GSTIN column and no invoice /
  voucher / tax columns (Tally List of Accounts, Zoho Export Customers). A name with one GSTIN on the list is applied before the
  learnt names, also for customers missing from GSTR-1 (they then show as not reported, not as B2C). The user's choices still win.
- Matching is recon.ts reconSales(); B2CS, Table 8 and e-commerce 9(5) rows have no invoices and are compared by month (B2CS: books
  B2C entries carry a "B2CS month", default their invoice month, which the user can change or clear).
- Books by invoice date, GSTR-1 / 3B by return period. Shifts between months of the same year are not reconciling items (Tobin): they
  cancel out in the year statement and show only in the month views.
- Every item has a tool's reason; the user may pick another reason (one entry, or bulk on filtered / selected entries: customer, type,
  month, date, reason, search) and a remark; "Not a supply" takes an entry out of turnover (above the line). The statement groups by the
  reason used, so books + reasons = GSTR-1 by construction; "Difference not explained" is the residual (nil unless excluded entries are
  also in GSTR-1). GSTR-1 → 3B: RCM supplies, advances (4F), months with no 3B, then per 3B table (3.1(a) incl. advances, (b), (c), (e),
  3.1.1(ii)).
- Workbook Revenue_Reco_<GSTIN>_<FY>.xlsx: Read Me, Dashboard, Books_to_GSTR1, GSTR1_to_3B, Month_wise, B2C_Month, Month_3B, Rev_Items
  (yellow columns Your reason / B2CS month / Remark with drop-downs; "Reason used" is a formula), G1_Rows, 3B_Rows, Books_Lines, Ledgers,
  Audit, Lists. Statements are SUMIFS over Rev_Items / G1_Rows / 3B_Rows, so reasons changed in Excel move the statement. Dropping the
  saved workbook with the same files reads the yellow columns back (by Id). Decisions are also kept in the browser per GSTIN + FY.
- Tests: test/revenue.test.ts on test/fixtures/revenue (make_revenue_fixtures.py: nine planted differences, register and GL routes);
  `python3 scripts/flow_recalc.py <workbook>` works for this workbook too (1,020 formulas, 0 mismatches on the demo).
- Not done: GSTR-1A, e-invoice / e-way bill data (agreed to leave out), multi-GSTIN, 3B JSON (PDFs only), HSN-wise comparison.

## Matching settings (v0.12, asked by Tobin 21 Nov 2026)
- Every tab has a "Matching settings" step (src/settings.ts, card #setcard) after Confirm client & year and before any matching.
  Tab order is now Input Reco, GST ledger flow, Revenue reco, Annual return (last). Settings are kept in the browser per tab
  (`jjset:<tab>`; the old shared `jjmatch` seeds Input Reco and Annual return), each section shows an "In use" line, and the
  same lines (`describe()`) go into the Read Me of the flow and revenue workbooks (Recon sheets keep describeMatch in G3).
- Input Reco / Annual return: the invoice rules, presets, tolerance ₹ / %, date window, amounts compared (moved out of Review
  matches, which now only says what it matched with) and the supplier-name similarity for suggestions.
- GST ledger flow: equal-within ₹ (engine TOL), which rules may explain a difference (netted on portal, tax head, timing,
  after the period, fee booked to tax; Inputs.opts.rules), timing windows (same entry up to 3 months, month totals up to 2),
  and the invoice rules for ITC three ways (itcThreeWay match). The structural "compared in total" head item always runs.
- Revenue reco: the invoice rules (no supplier totals) and how a books customer without a GSTIN gets one, in this order:
  your choice, customer list, same name in books (bookKeys: names that carry the GSTIN on other entries), invoice no. AND
  amount agreeing with GSTR-1 documents of exactly one GSTIN (applied without asking, or suggested only; minimum invoices).
  resolveCustomers() returns the GSTIN and basis per name; step 4b lists mapped customers with the basis and the agreeing
  invoices, "not right? choose" stores '?' (no automatic mapping); the Customer_Map sheet carries the same. A number that agrees
  with a different amount is shown but never maps.

## Fixes from the independent review (v0.13, 21 Nov 2026)
Review: project files reviews/GST_Reco_Tool_Review_v0.12.md. Tested by test/review.test.ts.
- **2B amendments** (GSTN GSTR-2B FAQ 8: amendment tables carry the full revised values, only the summary is the difference):
  process2b() handles files in period order and links B2BA/ECOMA by `oinum`, CDNRA by `ontnum`, re-sent bills of entry
  (`isamd` Y) by BOE no. The original (or an earlier amendment) gets key '' and column S "Superseded by ..."
  (`isSuperseded()`), so 8A, Input Reco and ITC three ways count the latest version only. An amendment whose original is
  not loaded is not counted (warning: load the original month's 2B).
- **Purchase debit notes / returns / vendor credits** stay negative in Books_Purchase (new mapping field Document type;
  a negative row is a return too). Purchase and 2B documents carry `cls` 'N' for notes, so a note is never paired with the
  invoice of the same number (ids get `|CN`).
- **A return loaded twice**: a GSTR-1 or 2B file of a period already loaded whose entries are at least half the same is left
  out with an error message; parts of a large return (different documents) are still added up.
- **CSV**: numbers with leading zeros stay text (invoice no. 000123). Register dates written as text are checked as a column:
  month/day/year only when a second part is above 12 and no first part is (shown on the mapping preview).
- **Speed**: pair() looks candidates up in indexes (by GSTIN, digits, last 4 characters / tail digits, number) instead of
  scanning every 2B document; supplier totals and hints use groups. 50,000 documents a side: 19 s → under 1 s (Node).
- **Progress bar** (src/progress.ts, `step()` / `withProgress()`): reading files (file i of n), working out the tabs
  (once after the last file, not after each one), and every workbook build. step() waits for a paint, and does nothing in Node.

## Saved workpapers bring everything back (v0.14, asked by Tobin 21 Nov 2026)
Tobin: the second time, the saved workpaper alone should be enough; returns and portal ledgers never change, only the
books files (sales / purchase register, GL dump, customer list) may be replaced.
- Every workbook the tool writes (ITC recon, GSTR-9, flow, revenue) gets two hidden sheets (src/state.ts `addStateSheets`):
  `_JJState` = JSON of the settings and choices (store keys: `jjset:<tab>` as in use, register mappings `jjmap:*` and
  register defaults `jjmapd:*` (not the claim year), this client's supplier names `jjalias` (names in its purchase register,
  else GSTINs in its 2B), flow `jjflow:acc:<gstin>` / `jjflow:<gstin>:<fy>`, revenue `jjrev:<gstin>:<fy>` / `jjrev:cls:` /
  `jjrev:cust:`), plus GSTIN, FY, legal name; `_JJFiles` = a zip (base64) of every source file in use (`InFile.raw`, the bytes
  as dropped; workbooks are never included). Both are split over A2, A3... (32,000 characters a cell) and survive a re-save
  (tested with LibreOffice in test/state.test.ts). A rebuild from a dropped workpaper replaces the two sheets.
- Dropping a workpaper (classify reads `_JJState`; the flow workbook is now recognised as 'Flow workbook'): `applyState`
  writes the keys to the browser (settings and per-entry choices: the workpaper wins; name → choice maps are merged), the
  source files are classified again and listed with "from the workpaper", the page switches to the workpaper's tab, and
  Matching settings shows "Restored from ..." with what came back and "Keep my earlier settings instead" (`undoState`).
  Revenue: the yellow columns of Rev_Items are still read back after the saved state, so edits made in Excel win.
- A Register / Books ledger / Customer list dropped with (or after) the workpaper replaces the workpaper's copy of the same
  thing (register: same purchases / sales kind; books: the same dump format or the same single ledger). Returns and portal
  ledgers are never replaced (an identical file is skipped as before; a second copy of a period is caught by the v0.13 check).
- Annual / Input Reco: the register restored from the workpaper rebuilds Books_Purchase / Books_Sales, as dropping the register
  again did before; lines corrected by hand in those sheets are replaced (remove the register from the file list to keep them).
- The browser store keeps values in memory when localStorage is blocked, so a restore also works in a private window.

## Key decisions (agreed with Tobin)
- No macros and no Excel 365 functions (SUMIFS/INDEX/MATCH only). The browser does the parsing, because Power Query "From PDF" isn't available to every user.
- Hosting: the single HTML on a shared drive works offline; optional Cloudflare Pages at gst.jjglobal.in behind Cloudflare Access.
- Branding: James & James design system (#2C388E, Onest on the web page, Arial in Excel). Every sheet says "Prepared by James & James LLP".
- ICAI Technical Guides followed: 7I includes 7E; 7F = 4N − 4G + 10 − 11; 9Q = Table 9 + Table 14; 12E/14S = 7J; 8B = 6B only; rule 37/37A reclaims go to 6H, other prior-year reclaims to 6A1; next-FY returns count for April–October only (filed up to 30 Nov; ICAI TG Dec 2025 FAQ 3, agreed with Tobin 21 Nov 2026), and next-FY credit notes in them are tagged 11-REVIEW.
- GSTR-9C FY 2025-26: self-certified. No Part B / DSC in the offline tool, so the JSON can be generated directly (not built yet).
- Supplier names (v0.8): books lines without GSTIN get it from 2B only by exact normalised name (automatic), by a name the user confirmed in step 2c of the Loader (approximate match: typo-tolerant tokens, bigrams, initials, invoice-no. hits; remembered in the browser, src/suppliers.ts), or by invoice no. + amount. The old automatic substring guess was removed.
- Review step (v0.8, loader step 4, src/review.ts): runs reconPreview() (build.ts) in the browser before building, for purchases vs 2B and sales vs GSTR-1. Matching options (MatchOptions in recon.ts: rules on/off, tolerance Rs and %, date window, tax-only or taxable+tax; presets Strict / Standard / Lenient; Standard default has a ±3-day window) are saved in the browser and printed in G3 of Recon_Purchases / Recon_Sales. KPI tiles, Suppliers and Invoices views with filters and filtered / selected totals, manual Match selected (codes M001...), Unmatch (documents kept apart = Match code X, read back on refresh), undo list, and Download this view (.xlsx, src/xlsxmini.ts). Tests: test/match.ts.
- Matching order: manual codes, then invoice no. (punctuation ignored), digits, last digits/tail (amounts agree), GSTIN+date+amount, number+amount with GSTIN differing, supplier totals, then hints. Missing GSTIN is taken from 2B by supplier name or by invoice no. + amount. Zero-tax lines are not compared. Tolerance ₹1.
